# 为什么重写：WPF 版内存与帧率实测

这份数据是重写的依据，也是 Rust 版的性能门槛来源。测量时间 2026-11-02，
机器：6016×3384@200%（6K）、Intel 核显、16 核、60 Hz，Windows 11。

测量工具当时放在 `build/probe/`（已随 `build/` 被 git 忽略，未归档）：
`MemProbe.exe` 做全链路检查点、`LadderProbe.exe` 逐层搭窗口、`DecodePeak.exe` 量解码峰值。

---

## 1. 进程总量

| 状态 | private | working set |
|:--|--:|--:|
| 刚启动、线带收起 | 120–129 MB | 156 MB |
| 线带放下、6 张卡片 | 216 MB | 267 MB |
| 老版本进程（已跑 45 分钟） | 343 MB | 342 MB |
| 一次 6K 截图过程中的峰值 | 355 MB | 505 MB |
| 其中托管堆 | **4.6 MB** | — |
| 其中大对象堆 | 2.7 MB | — |

结论：托管内存只有几 MB，**几乎所有内存都是 WPF 的原生表面**，不是泄漏。

## 2. 归因

| 项 | 增量 | 说明 |
|:--|--:|:--|
| 空的不透明窗口（6016×420） | +74 MB | 其中约 43 MB 是首个窗口触发的 D3D 设备固定开销 |
| 同样窗口改分层透明 | +29 MB | 逐像素透明要走 CPU 合成 |
| 线带窗口 + 6 张卡片 | **+185～205 MB** | 6016×420 的分层窗口，动画 10 s 内存稳定不增长（表面池上限） |
| 24 个 `DropShadowEffect` | ~28 MB | 每个特效一份中间表面 |
| 飞行窗口（3008×3264 量级） | +50～180 MB | 覆盖整条飞行路径；结束后隐藏但表面仍被池化 |
| 软件渲染对照（线带 + 6 卡） | 91 MB | 但飞行帧率从 60 掉到 36–45 |

## 3. 一次性峰值

| 操作 | 旧实现 | 优化后 |
|:--|:--|:--|
| 6K 图判重（`SamePicture`） | 294 ms，峰值 +237 MB | 90 ms，峰值 +23 MB |
| 剪贴板 alpha 检查 + 哈希 | 各拷一份全尺寸 `byte[]`（6K 约 80 MB/份） | 条带扫描，≤ 2 MB |
| 编辑时保留原图 | 81 MB（全尺寸） | 9.4 MB（2048 px） |

## 4. 帧率

| 场景 | WPF 基线 | 调优后 |
|:--|--:|--:|
| 全屏透明窗口 + 飞行内容 | 8.7 fps | 46–61 fps（包围盒窗口、1600 px 上限、飞行不画阴影、窗口复用） |
| 2266×2392 飞行 | 33.2 fps | 58.6–61 fps |
| 线带空闲 | — | 单核约 4.2% |

调优的每一项都是在绕过 WPF 的默认行为：窗口只覆盖路径、起飞尺寸封顶、
阴影延后、逐帧布局改复用对象、重活挪出 UI 线程。**框架本身没有为这种负载设计。**

## 5. 对 Rust 版的要求

| 指标 | WPF 现状 | Rust 目标 |
|:--|--:|--:|
| 私有内存（空闲，6 卡） | 216 MB | ≤ 35 MB |
| 私有内存（全屏飞行） | 355 MB | ≤ 80 MB |
| 空闲 CPU（线带放下） | 4.2% 单核 | ≤ 2% |
| 飞行帧率 | 46–61 fps | ≥ 59.5 fps |
| 冷启动到托盘 | ~300 ms | ≤ 300 ms |

架构上必须避免：

1. 整窗 CPU 光栅（`UpdateLayeredWindow` 那条路）；
2. 每个窗口一份系统内存表面；
3. 特效每帧重新模糊；
4. 全尺寸中间位图（解码、比较、编码）；
5. UI 线程上的渲染阻塞（`Present` 要在渲染线程）。

见 `docs/ARCHITECTURE.md`。
